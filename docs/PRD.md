# 네이버 블로그 자동 작성 오케스트레이터 PRD

## 1. 개요 (Overview)

- **목적**: 기존에 개별적으로 존재하는 3개의 도구
  - 크롤링 모듈(`NaverBlogCrawlingByPlayWright/blogcontentsClawring.py`)
  - AI 글 작성 지침(`PostResult/AGENTS.md`) 기반 `codex exec` 글 생성
  - 자동 발행 모듈(`NaverAutoWrite/main.py`)

  를 하나의 GUI 프로그램에서 순서대로 실행하여, "정보 입력 한 번으로 네이버 블로그 글 작성까지" 자동화한다.
- **핵심 가치 제안**: 수동으로 크롤링 스크립트 → `codex exec` 실행 → 발행 스크립트를 각각 터미널에서 실행하던 과정을 하나의 데스크톱 GUI로 통합하여, 입력(이미지/키워드/코멘트)만으로 파이프라인이 끝까지 진행되도록 한다.
- **대상 사용자**: 1인 블로거(이 저장소 소유자), 반복적으로 여행/제품 후기 블로그 글을 작성하는 사용자.

## 2. 목표 및 성공 지표 (Goals & Success Metrics)

### 정성적 목표
- 이미지 + 키워드 + 메모 입력만으로 네이버 블로그 발행까지 무중단으로 진행된다.

### 정량적 지표
- 전체 파이프라인(크롤링 ~ 발행) 소요 시간.
- 단계별(크롤링/AI 생성/발행) 실패율.
- 재시도 없이 1회 실행으로 발행까지 도달하는 비율.

### Out of Scope (비범위)
- 다중 블로그 계정 동시 처리.
- 예약 발행.
- 이미지 자동 보정/편집.
- `PostResult/AGENTS.md`의 문체/페르소나 내용 자체를 프로그램이 자동 생성/수정하는 기능.
- 요구사항 원문 및 "기존 구성요소 계약"에 명시되지 않은 모든 기능(위 항목에 한정하지 않고, 원문에 없는 것은 전부 비범위로 간주한다).

## 3. 사용자 시나리오 (User Flow)

### 탭 구성안
- **입력 탭**: 이미지 드래그 드롭 + 뷰어, 키워드 입력, 사용자 추가 코멘트 입력.
- **AGENTS.md 편집 탭**: `PostResult/AGENTS.md` 조회/편집 텍스트 영역.
- **실행/로그 탭**: 크롤링 실행 → AI 글 생성 → 발행까지 순차 진행 상황을 로그/프로그레스로 표시.
- **결과 탭**: `PostResult` 하위에 생성된 폴더/파일 목록과 발행 결과 요약 확인.

### 정상 흐름 (Happy Path)
1. 사용자가 입력 탭에서 이미지(0장 이상)를 드래그 드롭으로 첨부하고 뷰어로 확인한다.
2. 키워드를 입력한다.
3. 사용자 추가 코멘트(선택)를 입력한다.
4. 필요 시 AGENTS.md 편집 탭에서 내용을 확인/수정하고 저장한다.
5. 실행/로그 탭에서 실행 버튼을 누르면 다음이 순차 진행된다.
   1. 키워드로 크롤링 서브프로세스(`blogcontentsClawring.py`) 실행.
   2. 크롤링 결과 txt 파일을 작업 폴더 `blog/`로 복사.
   3. 첨부 이미지를 작업 폴더 `images/`로 복사.
   4. 이미지 경로, 키워드, 사용자 코멘트, `AGENTS.md` 내용, 크롤링 결과 txt를 결합하여 `codex exec` 서브프로세스 실행.
   5. 생성 결과를 작업 폴더 `output/{제목}.md`, `output/{제목}_naver.html`로 저장.
   6. `output/{제목}.md`를 `--md` 인자로 전달하여 `NaverAutoWrite/main.py` 서브프로세스 실행, 네이버 블로그에 발행.
6. 결과 탭에서 생성된 폴더/파일 목록과 발행 결과를 확인한다.

### 예외 흐름
- **이미지/사용자글이 없는 경우**: 요구사항 원문에 "이미지와 사용자글은 없을 수도 있다"고 명시되어 있으므로, 이 경우도 정상 흐름으로 처리하며 파이프라인은 중단 없이 진행된다.
- **크롤링 결과가 0건인 경우**: 크롤링 단계가 0건을 반환하면 실행/로그 탭에 명확히 표시하고, 이후 AI 생성 단계에는 크롤링 결과 txt 없이(또는 빈 입력으로) 진행할지 여부를 사용자에게 알린다(세부 정책은 7절 리스크 참조).
- **`codex exec` 실행 실패/타임아웃**: 실패 사유(표준에러, 종료 코드, 타임아웃 여부)를 로그에 표시하고 해당 단계에서 파이프라인을 중단한다.
- **네이버 로그인 실패/CAPTCHA**: `NaverAutoWrite`의 기존 리스크를 그대로 계승하며, 발행 단계 실패로 표시하고 이전 단계(크롤링/AI 생성) 산출물은 `PostResult`에 유지한다.
- **[추가 확정 요구사항] 크롤링 미사용 선택 시**: 사용자가 입력 탭에서 크롤링 토글을 "미사용"으로 선택한 경우, 크롤링 단계 자체를 건너뛰고 곧바로 이미지 복사 및 AI 생성 단계로 진행하는 정상 분기로 처리한다(오류 아님). 상세 처리 로직은 4.3 참조.

| 항목 | 내용 |

| **처리 로직** | 1. **[추가 확정 요구사항]** 4.1의 크롤링 사용 여부 토글이 "사용"(기본값)인 경우에만 아래 2~4단계를 수행하고, "미사용"으로 선택된 경우 크롤링 서브프로세스를 호출하지 않고 곧바로 이미지 복사 단계(4.6)로 진행한다.<br>2. `python blogcontentsClawring.py --keyword <키워드> --count <1~100> --mode http [--headless]` 형태로 서브프로세스 호출<br>3. 실행은 `NaverBlogCrawlingByPlayWright` 폴더 및 해당 폴더 `.env`(NAVER_CLIENT_ID, NAVER_CLIENT_SECRET) 기준으로 진행<br>4. 산출물인 `result/YYYYMMDD/{안전한제목}_{YYYYMMDD_HHMMSS}.txt` 파일(들)을 확인하여 `PostResult/<날짜_제목>/blog/`로 복사<br>5. **[추가 확정 요구사항, 검증 반영]** `result/YYYYMMDD/` 폴더는 과거 실행 산출물과 공유되므로, 이번 실행 산출물만 식별하기 위해 크롤링 서브프로세스 실행 직전 해당 폴더의 파일 목록을 스냅샷하고, 실행 후 신규 생성된 파일만(또는 파일명의 `_{YYYYMMDD_HHMMSS}` 타임스탬프가 실행 시작 시각 이후인 파일만) `blog/`로 복사 대상으로 식별한다.<br>6. **[추가 확정 요구사항]** 크롤링 "미사용" 시 `PostResult/<날짜_제목>/blog/` 폴더는 비어있거나 생성되지 않으며, 4.4(AI 글 생성) 단계의 `codex exec` 프롬프트는 크롤링 결과 txt 입력 없이 이미지/키워드/사용자 코멘트/AGENTS.md만으로 구성된다. |

### 4.4 AI 글 생성 (codex exec 연동)

| 항목 | 내용 |
|---|---|
| **설명** | `codex exec` 명령어를 서브프로세스로 호출하여 이미지, 키워드, 사용자 코멘트, `AGENTS.md`, 크롤링 결과 txt를 결합한 프롬프트로 글을 생성 |
| **입력** | 첨부 이미지 파일 경로 목록, 키워드, 사용자 코멘트, `PostResult/AGENTS.md` 내용, 4.3의 크롤링 결과 txt(크롤링 "미사용" 시 없음) |
| **처리 로직** | 1. 이미지 경로 목록, 키워드, 사용자 코멘트, `AGENTS.md` 내용, 크롤링 결과 txt 5가지 입력을 하나의 프롬프트(또는 프롬프트+첨부 형태)로 결합. **[추가 확정 요구사항]** 4.1/4.3에서 크롤링이 "미사용"으로 선택된 경우, 크롤링 결과 txt 입력 없이 이미지/키워드/사용자 코멘트/AGENTS.md 4가지만으로 프롬프트를 구성한다.<br>2. **[추가 확정 요구사항, 검증 반영]** 프롬프트에 포함하는 이미지 경로는 `NaverAutoWrite/image_uploader.py`가 `Path(image_path).exists()`로 **`NaverAutoWrite` 폴더를 CWD로 하여 경로를 해석**한다는 점을 전제로, `codex exec`가 생성하는 md 내 `![대체텍스트](경로)`의 경로는 반드시 **절대경로**로 작성하도록 프롬프트 지시문에 명시한다. 상대경로를 절대경로로 강제 치환할 수 없는 경우, 4.5 실행 직전 오케스트레이터가 md 내 이미지 경로를 절대경로로 후처리 치환한다.<br>3. **[추가 확정 요구사항, 검증 반영]** 산출물 파일명 `{제목}` 및 md 내부 `# H1` 제목은 동일한 원본 제목 문자열에서 파생되어야 하며, 파일명으로 사용 시 Windows 예약 문자(`\ / : * ? " &lt; &gt; |`)를 제거/치환하는 안전화 규칙을 적용한다(크롤러의 `_safe_folder_name`과 동일한 방식을 채택).<br>4. **[추가 확정 요구사항, 검증 반영]** 크롤링 결과 txt를 프롬프트에 결합할 때 총 문자 수 상한(기본값은 7절 리스크에서 결정)을 두고, 상한 초과 시 건수를 줄이거나 앞부분만 사용하는 등 절단 정책을 적용한다.<br>5. `codex exec` 서브프로세스 실행(정확한 CLI 인자·입력 전달 방식은 7절 리스크 참조)<br>6. 생성 결과를 "기존 구성요소 계약 B"에 따라 저장 |
| **출력** | `PostResult/<날짜_제목>/output/{제목}.md`, `PostResult/<날짜_제목>/output/{제목}_naver.html` |
| **완료 조건(Acceptance Criteria)** | `codex exec` 정상 종료 시 `output/{제목}.md`와 `output/{제목}_naver.html`이 모두 생성됨, 생성된 md 파일의 첫 번째 `# H1`이 제목으로 사용 가능한 형식임(4.5 입력 규칙과 정합), 파일명 `{제목}`이 파일시스템 안전화 규칙을 통과함, **md 내 이미지 경로가 모두 절대경로이거나 발행 전 절대경로로 치환됨(4.5에서 이미지 누락 없이 첨부됨을 확인하는 전제 조건)**, 실패/타임아웃 시 예외 흐름(3절)에 따라 처리됨, **[추가 확정 요구사항, 사용자 요청] 사용자가 첨부한 이미지가 있으면 AI가 본문에서 언급하지 않았더라도 첨부 이미지 전부가 최종 md 본문에 반드시 포함됨**(AI에게 먼저 지시하되, 생성 직후 md를 검사해 누락된 첨부 이미지를 코드 레벨로 강제 삽입하는 이중 보장 — `pipeline._ensure_attached_images_included`) |

| 항목 | 내용 |
|---|---|
| **설명** | 파이프라인 산출물을 작업 단위 폴더 규칙에 따라 `PostResult` 하위에 저장 |

(결정 필요) 파이프라인 실행 로그/메타데이터(키워드, 실행 시각, 각 단계 성공/실패, 발행 URL 등)를 `PostResult/<날짜_제목>/result.json` 등으로 저장할지 여부는 7절 리스크 참조<br>4. **[추가 확정 요구사항, 검증 반영]** 동일한 `<날짜_제목>` 폴더가 이미 존재하는 경우(같은 날짜에 같은 제목으로 재실행하는 경우 포함), 기존 폴더를 덮어쓰지 않고 폴더명에 순번 접미사(예: `_2`, `_3`)를 붙여 새 폴더로 생성한다. 발행 단계만 재시도하고자 하는 경우의 재개 절차는 7절 리스크(M-1) 참조 |

### 4.8 태스크 저장/관리 (사용자 확정 요구사항)

| 항목 | 내용 |
|---|---|
| **설명** | 항목별(키워드+이미지+크롤링/AI 이미지 생성/로그인 방식 설정)로 작업 정의를 미리 만들어 디스크에 저장해 두고, 필요할 때 골라서 기존 "전체 실행" 대기열(4.7과 동일한 실행 엔진)에 넣을 수 있는 기능. "입력" 탭의 즉시 실행 흐름과는 별개이며, "멀티 작업" 탭이 태스크 관리자 역할까지 겸한다. |
| **입력** | 태스크 이름, 키워드, 코멘트, 이미지 파일 경로 목록, 크롤링 사용 여부, AI 이미지 생성 여부(+생성 개수, 1~10장), 로그인 방식(자동/수동) |
| **처리 로직** | 1. "멀티 작업" 탭에서 새 태스크 생성/기존 태스크 편집(같은 다이얼로그, 입력 탭과 동일한 필드 구성)<br>2. 태스크 목록은 `tasks.json`(오케스트레이터 실행 위치 기준, exe 빌드 시 exe 옆)에 매 변경(추가/수정/삭제/순서변경)마다 즉시 저장 — 앱을 재시작해도 유지됨<br>3. 이미지는 원본 경로만 저장하고 복사하지 않음(실제 파일 복사는 태스크가 대기열에 들어가 파이프라인이 실행될 때 기존 로직이 처리)<br>4. "대기열에 추가"/"전체 대기열에 추가"를 누르면 선택된(또는 전체) 태스크를 `PipelineContext`로 변환해 기존 `JobQueueManager.enqueue()`에 그대로 넘김 — 실행 엔진 자체는 변경하지 않음<br>5. 태스크는 대기열에 넣어도 목록에서 삭제되지 않음(반복 재사용 가능한 정의로 취급)<br>6. 삭제/순서 변경(위/아래) 지원<br>7. **[스코프 제외]** 입력 탭의 "기존 데이터 검색"(크롤링 결과 재사용) 기능은 태스크 편집 다이얼로그에 포함하지 않는다 — 태스크로 실행한 작업은 항상 새 작업 폴더로 진행됨<br>8. **AI 이미지 생성 개수 지정**: "AI 실사 이미지 생성" 체크박스 옆 스핀박스(1~10, 기본 1)로 태스크별/즉시실행별 생성 장수를 지정한다. `codex exec` 프롬프트에 요청 장수를 명시하고, codex가 그보다 많이 만들어도 먼저 생성된 순서로 요청한 장수만 채택한다(`pipeline.run_image_generation`)<br>9. **대기 중 작업 취소**: "멀티 작업" 탭의 "대기 중 작업" 목록에서 아직 시작되지 않은 작업을 선택해 "선택한 대기 작업 삭제" 버튼으로 대기열에서 제거할 수 있다(`JobQueueManager.remove_pending`). 이미 진행 중인 작업은 취소 대상이 아니다 |
| **출력** | `tasks.json`(태스크 목록 영속화), 대기열에 추가된 `PipelineContext`(4.7 실행 엔진 입력) |
| **완료 조건(Acceptance Criteria)** | 태스크 생성/편집/삭제/순서변경이 즉시 화면과 `tasks.json`에 반영됨, 앱을 재시작해도 태스크 목록이 유지됨, "대기열에 추가"로 넣은 태스크가 정확히 같은 설정으로 파이프라인이 실행됨, 손상된 `tasks.json`이 있어도 빈 목록으로 시작하며 앱 실행이 막히지 않음 |

### 4.9 다중 네이버 계정 발행 (사용자 확정 요구사항)

| 항목 | 내용 |
|---|---|
| **설명** | 여러 네이버 계정으로 블로그 글을 발행할 수 있도록, 태스크(글)마다 사용할 계정을 지정하는 기능. `NaverAutoWrite`는 `.env` 하나에서만 자격증명을 읽는 단일 계정 전제이므로(4.5), 이 기능은 `NaverAutoWrite`의 코드/CLI 계약을 변경하지 않고 오케스트레이터 쪽에서 계정별 자격증명을 서브프로세스에 주입하는 방식으로 구현한다. |
| **입력** | 계정 목록(표시 이름/네이버 아이디/비밀번호/블로그ID/카테고리, `accounts.json`), 각 태스크의 `account_id` |
| **처리 로직** | 1. "계정 관리" UI에서 `accounts.json`(오케스트레이터 실행 위치 기준, 평문 저장 — 저장소에 커밋되지 않도록 `.gitignore` 등록)을 추가/수정/삭제<br>2. 입력 탭/태스크 편집/대기열 일괄 설정 각각에 "발행 계정" 드롭다운을 두어 태스크마다 독립적으로 계정을 지정(미지정 시 기존 동작대로 `NaverAutoWrite/.env`의 기본 계정 사용)<br>3. 발행 단계에서 지정된 계정의 자격증명(`NAVER_ID`/`NAVER_PW`/`NAVER_BLOG_ID`/`NAVER_CATEGORY`)을 서브프로세스 환경변수로 주입 — `python-dotenv`의 `load_dotenv()`가 이미 설정된 환경변수를 덮어쓰지 않는 특성을 활용하므로 `NaverAutoWrite/config.py`는 그대로 둔다<br>4. 계정마다 다른 `--session-file` 경로(`NaverAutoWrite/.naver_session/{account_id}/`)를 지정해 로그인 세션(크롬 프로필)을 계정별로 분리<br>5. **[검증 반영] 크롬 CDP 포트 고정 문제**: `NaverAutoWrite/naver_login.py`가 CDP 포트(고정값 9333)에 이미 떠 있는 크롬을 무조건 재사용하므로, 세션 파일 경로만 바꿔서는 계정이 섞일 수 있다 — 직전 발행 계정과 이번 계정이 다르면 발행 전에 그 포트를 점유한 크롬 프로세스를 오케스트레이터가 강제 종료한 뒤 진행한다(`pipeline._kill_chrome_on_cdp_port`). 이 때문에 서로 다른 계정의 발행은 동시 실행이 아니라 대기열 순서대로 순차 실행되어야 한다(기존 `JobQueueManager`가 원래 한 번에 하나만 실행하므로 추가 제약은 없음) |
| **출력** | `accounts.json`(계정 목록 영속화), `last_account.json`(직전 발행 계정 기록 — 크롬 재시작 판단용) |
| **완료 조건(Acceptance Criteria)** | 계정 추가/수정/삭제가 즉시 `accounts.json`에 반영됨, 태스크마다 지정한 계정으로 발행 시 해당 계정의 자격증명/블로그ID가 사용됨, 연속된 두 발행의 계정이 다르면 그 사이에 크롬이 재시작되고 같으면 재시작되지 않음, `accounts.json`이 없거나 손상돼도 앱 실행이 막히지 않고 기본 계정(.env)으로 동작함 |

## 5. 비기능 요구사항 (Non-Functional Requirements)

- **기술 스택**: Python 기반(기존 저장소 전체가 Python). GUI 프레임워크는 7절 "리스크 및 오픈 이슈"에서 결정 사항으로 다룬다. 기존 `blogCrawlingUI.py`는 tkinter를 사용하나, 드래그 앤 드롭/이미지 뷰어/탭 UI 요구사항과의 적합성은 검토가 필요하다.
- **[명시] 스택 범위 한정**: 본 프로젝트는 **Python 데스크톱 GUI 애플리케이션**이며, 웹 프레임워크(Next.js/React 등), 데이터베이스, REST/GraphQL API 서버를 포함하지 않는다. 화면은 라우트가 아닌 GUI 프레임워크의 탭/윈도우로 구성되고, 영속 데이터는 데이터베이스가 아닌 파일시스템(`PostResult/` 하위 폴더 및 각 서브 프로젝트의 `.env`)에 저장된다.
- **[명시] 테스트 전략**: 크롤링/`NaverAutoWrite` 서브 프로젝트 내부에서 사용하는 Playwright(브라우저 자동화)는 각 서브 프로젝트의 기존 구현 범위이며, 본 오케스트레이터 GUI 자체의 테스트에는 웹 브라우저 기반 E2E 도구(예: Playwright MCP)를 적용할 수 없다. GUI 자체 검증은 수동 QA 체크리스트 또는 사용 GUI 프레임워크에 맞는 데스크톱 테스트 도구(예: `pytest` + 프레임워크별 GUI 테스트 유틸)로 대체한다.
- **실행 환경**: Windows 로컬 환경 기준(크롤링/AI 생성/발행 3개 서브 구성요소 모두 Windows 로컬 실행 전제).
- **프로세스 관리**: 크롤링 스크립트, `codex exec`, `NaverAutoWrite`의 3개 외부 프로그램을 서브프로세스로 호출 시 타임아웃, 표준출력 스트리밍, 종료 코드 처리 정책이 필요하다.
- **[추가 확정 요구사항, 검증 반영] 경로/인코딩 처리**: `PostResult/<날짜_제목>/` 등 한글·공백이 포함된 경로를 서브프로세스 인자로 전달할 때는 셸을 경유하지 않고 인자를 리스트 형태로 전달하며, 경로는 절대경로로 정규화한다. 서브프로세스의 표준출력/표준에러를 캡처할 때는 인코딩을 UTF-8로 명시하여 한글 로그 깨짐을 방지한다.
- **에러 핸들링**: 크롤링/AI 생성/발행 각 단계의 실패를 독립적으로 감지하고, 사용자에게 어느 단계에서 실패했는지 명확히 표시한다.
- **보안**: 각 서브 프로젝트의 `.env`(NAVER_CLIENT_ID/NAVER_CLIENT_SECRET, NAVER_ID/NAVER_PW/NAVER_BLOG_ID/NAVER_CATEGORY 등) 자격증명은 오케스트레이터가 별도로 저장하지 않고, 각 서브 프로젝트 폴더의 기존 `.env` 파일을 그대로 참조한다.
- **로깅**: 파이프라인 단계별 진행 상황을 콘솔과 GUI에 동시 출력한다.

## 6. 기술 설계 개요 (Technical Design Overview)

### 모듈 구조 제안
- `app.py` — GUI 진입점.
- `pipeline.py` — 크롤링 → AI 생성 → 발행 오케스트레이션.
- `agents_editor.py` — `PostResult/AGENTS.md` 조회/편집.
- `image_input.py` — 드래그 드롭/뷰어.
- `subprocess_runner.py` — 3개 외부 프로그램(크롤링, `codex exec`, `NaverAutoWrite`) 서브프로세스 공통 실행기.

### 서브 구성요소 호출 방식
- `NaverBlogCrawlingByPlayWright/.venv`가 존재하는 등 각 서브 프로젝트가 독립된 `.venv`/의존성을 가지고 있을 가능성이 높으므로, 같은 파이썬 프로세스 내 import 방식이 아닌 **서브프로세스 실행을 기본 방향으로 제안**한다.

### 실행 시퀀스(텍스트 기반)
1. 입력 수집(4.1)
2. (선택) AGENTS.md 편집 저장(4.2)
3. 크롤링 서브프로세스 실행(4.3)
4. 크롤링 결과 `blog/`로 복사(4.3, 4.6)
5. 이미지 `images/`로 복사(4.6)
6. `codex exec` 서브프로세스 실행 — 프롬프트 조합(4.4)
7. 결과 `output/`에 저장(4.4, 4.6)
8. `NaverAutoWrite` 서브프로세스 실행 — `--md output/{제목}.md`(4.5)
9. 결과 요약을 `PostResult/<날짜_제목>/`에 기록(4.6, 4.7)

## 7. 리스크 및 오픈 이슈 (Risks & Open Questions)

> **[검증 반영]** 본 절은 prd-validator 에이전트의 기술 검증(코드 근거: `NaverAutoWrite/image_uploader.py`, `md_parser.py`, `main.py`, `NaverBlogCrawlingByPlayWright/blogcontentsClawring.py`)을 반영하여, 치명적 정합성 결함(이미지 경로 해석 불일치, 제목/파일명 이중 출처)은 4.4/4.5/4.6에 확정 요구사항으로 직접 반영했고, 아래 항목은 구현 초기 결정이 필요한 중요 리스크로 추가했다.

- **[검증 반영: M-1] 부분 실패 시 재시작/재개 정책 미확정**: 크롤링·AI 생성은 성공하고 발행 단계만 실패한 경우(로그인 실패/CAPTCHA 등), 처음부터 재실행하면 `codex exec`가 다른 제목/본문을 재생성하여 기존 `PostResult/<날짜_제목>/` 산출물과 불일치할 수 있다. 최소한 "발행 단계만 재시도"(기존 `output/{제목}.md`를 그대로 4.5에 재투입)하는 경로를 정의할지 결정이 필요하다. 폴더 충돌 시 순번 접미사 처리(4.6)와 연계된다.
- **[검증 반영: M-2] 프롬프트 길이/토큰 상한 미확정**: 크롤링 `--count`(최대 100건) 결과 전문을 `codex exec` 프롬프트에 결합할 때 총 문자 수 상한 값과 초과 시 절단/요약 정책의 구체적 수치가 결정 필요하다(4.4 처리 로직 4번 참조).
- **GUI 프레임워크 미확정** — **[해소]** `docs/ROADMAP.md` Task 001에서 **PySide6**로 결정함. 근거: (1) 여러 장 이미지 드래그 앤 드롭과 썸네일/뷰어를 네이티브 위젯(`QListWidget`+`dragEnterEvent`/`dropEvent`, `QLabel`+`QPixmap`)으로 지원해 `tkinter`+`tkinterdnd2`처럼 외부 확장 라이브러리에 의존하지 않는다. (2) `QTabWidget`으로 4탭(입력/AGENTS.md 편집/실행·로그/결과) 구성이 표준 API만으로 성숙하게 지원된다. (3) 배포 용량 증가라는 단점은 있으나, 이 프로젝트는 1인 사용자용 로컬 실행 도구로 배포 용량 제약이 크지 않다. 반대로 `tkinter`+`tkinterdnd2`는 표준 라이브러리 기반이라는 장점은 있으나 드래그드롭이 외부 확장(`tkinterdnd2`)에 의존하고 이미지 뷰어를 자체 구현해야 해 이번 요구사항(다중 이미지 드래그 드롭·뷰어·탭)에는 PySide6 대비 구현 비용이 크다고 판단함.
- **`codex exec`의 정확한 사용법** — **[부분 해소]** `docs/ROADMAP.md` Task 002에서 `codex exec --help`(codex-cli 0.144.4)를 실제로 확인함. 확인된 사실: 프롬프트는 위치 인자 또는 stdin으로 전달(`codex exec [OPTIONS] [PROMPT]`), 이미지는 `-i/--image <FILE>...`로 프롬프트 텍스트와 분리해 직접 첨부 가능, 작업 디렉터리는 `-C/--cd <DIR>`로 지정, 최종 응답은 `-o/--output-last-message <FILE>`로 파일 저장 가능, `--json`으로 이벤트 스트림을 JSONL로 받을 수 있음, `-s/--sandbox <read-only|workspace-write|danger-full-access>`로 샌드박스 정책 지정. `config.py`의 `build_codex_exec_args()`에 반영함. 다만 실제 실행 시 생성되는 `output/{제목}.md`/`{제목}_naver.html` 두 파일을 codex가 직접 그 경로에 쓰게 할지, `--output-last-message`로 받은 응답을 오케스트레이터가 저장할지는 아직 미정이라 "부분" 해소로 표시한다(Phase 3 Task 007에서 확정 필요).
- **크롤링 파라미터 기본값** — **[해소]** 크롤링 개수(`--count`) 기본값은 **3**으로 확정함(`config.CRAWLER_COUNT_DEFAULT`, 사용자 확정값). 모드는 계약대로 `--mode http`로 고정 사용하며 `browser` 모드는 노출하지 않는다. 개수를 GUI에서 사용자가 직접 조정할 수 있게 노출할지 여부는 아직 미정이다.
- **서브프로세스 인터프리터 경로** — **[해소]** `docs/ROADMAP.md` Task 002에서 하드코딩 대신 설정 기반 매핑(`config.py`의 `InterpreterConfig`/`DEFAULT_INTERPRETER_CONFIG`, 필요 시 `interpreters.json`으로 외부화)으로 결정함. 각 서브 프로젝트 폴더의 `.venv` 탐지 후 시스템 `python`으로 폴백하는 실제 탐지 로직은 Phase 3(Task 005/006/008)에서 구현한다.
- **AGENTS.md 편집 가드레일 필요 여부**: AGENTS.md 편집 기능이 저장 시 "기존 구성요소 계약 B"의 폴더 규칙 등 구조적 내용까지 사용자가 임의로 깨뜨릴 수 있는 리스크가 있어, 가드레일 도입 여부 결정이 필요하다.
- **저장 시점** — **[해소]** `docs/ROADMAP.md` Task 004에서 **명시적 저장 버튼** 방식으로 결정함(`app.py`의 `AgentsEditorTab`). 자동 저장은 사용자가 의도하지 않은 시점에 `PostResult/AGENTS.md`(페르소나/문체/폴더 규칙을 정의하는 핵심 계약 문서)를 되돌리기 어렵게 덮어쓸 위험이 있어 채택하지 않았다. "취소" 버튼은 마지막으로 로드/저장된 내용으로 복원한다.
- **발행 부가 인자 결정 필요**: `--blog-id`, `--headless`, `--session-file`을 GUI에서 설정할지, `NaverAutoWrite`의 기존 `.env` 값을 그대로 쓸지 결정이 필요하다.
- **파이프라인 메타데이터 저장 형식 미확정**: 실행 로그/메타데이터(키워드, 실행 시각, 각 단계 성공/실패, 발행 URL 등)를 `PostResult/<날짜_제목>/result.json` 등으로 저장할지 여부와 형식이 결정 필요하다.
- **단계 실패 시 후속 처리 미확정**: 단계별 실패 시 이후 단계를 자동 중단할지, 사용자에게 재시도/건너뛰기를 물을지 결정이 필요하다.
- **최소 입력 케이스의 프롬프트 구성 명확화 필요**: 이미지/사용자 코멘트가 모두 없는 최소 입력 케이스에서 `codex exec` 프롬프트 구성이 어떻게 달라지는지 명확화가 필요하다.
- **네이버 로그인 실패/CAPTCHA 리스크 계승**: `NaverAutoWrite`의 기존 알려진 리스크(로그인 실패, CAPTCHA 발생 가능성)를 본 오케스트레이터도 그대로 계승한다.
- **[검증 반영, 경미] `codex exec` 실행 CWD와 output 저장 주체 미확정**: `output/{제목}.md`·`{제목}_naver.html`을 `codex exec`가 직접 해당 경로에 쓰는지, 오케스트레이터가 별도 위치에서 생성된 결과를 이동시키는지 결정이 필요하다.
- **[검증 반영, 경미] `{제목}_naver.html`의 용도 미확정**: 발행 단계(4.5)는 `.md`만 사용하므로, `_naver.html`이 결과 탭 미리보기용인지 그 외 용도인지 명확화가 필요하다.
- **[검증 반영, 경미] AGENTS.md 동시 편집/실행 동시성 미확정**: 파이프라인 실행 중(4.4가 `AGENTS.md`를 읽는 시점)에 사용자가 4.2 편집 탭에서 동시에 저장하는 경우 어느 시점의 내용을 사용할지 결정이 필요하다.
- **[검증 반영] 로드맵 생성 시 웹 스택 템플릿 오적용 주의**: 본 프로젝트 로드맵을 `development-planner` 에이전트로 생성할 경우, 해당 에이전트의 기본 ROADMAP.md 템플릿은 Next.js App Router·데이터베이스/REST·GraphQL API·shadcn/ui·Playwright MCP 웹 E2E 테스트를 전제로 한다. 본 프로젝트는 5절에 명시한 대로 Python 데스크톱 GUI + 서브프로세스 오케스트레이션 구조이므로, 로드맵의 Phase/Task 구성 시 "라우트 구조", "DB 스키마", "REST API 구현", "Playwright MCP 웹 E2E" 항목을 그대로 적용하지 말고 "GUI 탭/윈도우 골격", "서브프로세스 실행기(`subprocess_runner.py`) 및 파이프라인(`pipeline.py`) 구현", "데스크톱 GUI 수동 QA 체크리스트"로 대체 해석해야 한다.
